# Data collection protocol (navd sessions)

How to turn robot drive time into training data, and how to know a
session is good. The pipeline: record on the robot → pull → extract →
label (SAM × depth) → review → count it.

## What a session contains

Each tick records both camera colors, lossless depth, the operator's
teleop twist, and odometry, plus the firmware's WebSocket stream: telemetry frames on `/runtime`
(mode, estop reason, operator and watchdog flags, per-wheel targets, bus
and power state at the 30 Hz subscription) and everything else on
`/runtime_events` (acks, errors, mode and E-STOP events, nav goals) and the camera
IMUs at 200 Hz. There is no navigation-goal concept in the
pipeline — the data is *what the robot saw* + *what you did*. The label
pipeline (SAM × depth fusion) turns that into drivable-area supervision
offline.

## Per-session checklist

Before:
- [ ] Jetson disk has headroom (`df -h /`; segments auto-prune at 20 GB)
- [ ] App connected, estop clear, wheels enable cleanly
- [ ] Know what this session is *for*: one line in the ledger

During (aim for 5–10 minutes of recorded drive time):
- [ ] Obstacle variety: drive near real clutter, around it, past it —
      the data only contains what you show it.
- [ ] Maneuver variety: straight runs, tight turns, approaches and
      stops, reversing out of tight spots.
- [ ] Lighting variety when possible (day, evening, lights off).
- [ ] Speed range: slow approaches, normal cruising, one decisive stop.
- [ ] A few near-misses (you correct late) — those ticks are gold.
- [ ] Note anything unusual (moved furniture, new obstacle) in the ledger.

After:
- [ ] Stop the recorder cleanly (Ctrl-C, or
      `sudo pkill -TERM -f 'record-nav[d]'` from a separate shell)
- [ ] `just pull-data` (mirrors to `datasets/sessions/`, extracts,
      audits) — check the audit line: 100% color, sensible depth medians
- [ ] Dashboard review pass (`just review`): sample ~20 ticks/session,
      paint corrections only where the fused teacher is actually wrong
- [ ] Ledger entry: session name, date, conditions, tick count, verdict

## Intent, events and places in the recording

Say what a drive is for before you arm, and mark moments as you go; the
recorder writes them into the drive MCAP so the file carries its own
labels (`/intent`, `/event`, `/place`, all `bebop.navd.*`). The intent is
sticky: it is written at the start of every segment and whenever it
changes, so a long drive that rolls over several files keeps it.

- By voice (the cascade brain has the tools): "I'm driving from the
  living room to the kitchen", "mark that sock as an obstacle", "mark a
  recovery start", "exclude that bit", "clear the drive intent".
- By HTTP on the vision process:

  ```sh
  curl -X POST http://bebop.local:9092/intent \
       -d '{"text": "living room to kitchen", "from": "living room", "to": "kitchen"}'
  curl -X POST http://bebop.local:9092/event -d '{"kind": "obstacle", "note": "sock at 1 m"}'
  curl -X POST http://bebop.local:9092/intent -d '{"clear": true}'
  curl http://bebop.local:9092/notes
  ```

  Event kinds are short tokens (`[a-z][a-z0-9_-]{0,31}`); the voice tool
  offers `obstacle` (a planted doll, sock, cable), `recovery` (an off-lane
  start on purpose), `exclude` (that stretch was a mistake) and `note`.
  Today they are recorded and listed per session in the ledger; extraction
  ignores `/event`, so an `exclude` mark does not yet drop ticks from the
  training data.

  Markers only land while a segment is recording (DialIn or RunPolicy,
  both wheels armed, no E-STOP). Outside a segment the route answers 409
  and the voice tool says "Not recording right now, so nothing was
  marked" instead of pretending; say "exclude that bit" before you disarm,
  and after an E-STOP note it in the ledger by hand. The intent can be
  set at any time, armed or not.
- Automatically: every time the 1 Hz scout recognises a taught place, a
  `/place` row (id, name, score) is written, so a drive carries its own
  from/to anchors for the place graph without you doing anything.

Turn-level intent (left / right / keep at a junction) needs no capture: it
is derived from the hindsight path.

## Ledger

`bebop-vision/datasets/sessions/sessions.jsonl` is generated by
`tools/session_ledger.py` (run by `just pull-data`) — one row per session:
duration, moving and reverse fractions, turn events, gyro gaps, intent,
events, places seen, and the firmware health log joined by time window. When evaluating a
navigation approach, the ledger tells you which questions the data can
answer — and which it can't.

## Commands

```sh
just collect     # ssh to the robot, start the recorder (--auto)
just pull-data   # mirror sessions -> extract -> audit
just review      # dashboard on :8099 (session replay + corrections)
```

Sessions land in `bebop-vision/datasets/sessions/` (extracted under
`datasets/navd-v0/<session>/`). The Jetson keeps only the newest ~20 GB
(`--disk-budget-gb`); pull before it prunes.

## What good coverage looks like

| dimension | minimum | good |
|---|---|---|
| sessions | 5 | 15+ |
| drive time | 15 min | 60+ min |
| obstacle layouts | 3 | 10+ |
| lighting conditions | 2 | 4+ |
| rooms/areas | 2 | every drivable area |

These thresholds are guidance, not gospel — the ledger's job is to make
the gaps visible, not to gate on numbers alone.
